# Decision D-045 — Branch notebook Markdown and Code cells

- **ID:** D-045
- **Date:** 8 October 2026
- **Question:** How should branch work notebooks separate narrative from executable work?
- **Context:** The prior notebook rendered all content from Python Code cells. The user clarified that this produced a poor reading flow and requested native Markdown and Code cells, with the title and data context presented before code.
- **Options considered:** Keep rendering Markdown from Code cells; place all content in Code cells; or use native Markdown for prose and Python Code cells for executable steps.
- **Evidence and source references:** Explicit user clarification on 8 October 2026; the current [biological data collection branch notebook](../../notebooks/branch_work/01_pipeline_biological_data_collection.ipynb), [notebook index](../../notebooks/README.md#branch-work-notebook-convention), and D-044's data-handling safeguards.
- **Decision:** Branch work notebooks must use native Markdown cells for titles, contributor metadata, purpose, scope, data context and explanatory narrative. Place these sections before the first Code cell. Use concise Python Code cells for checks and examples, divided into steps that follow the documented workflow. Use concise, formal prose with consistent headings, terminology and punctuation. Format branch names and identifiers as inline code; use heading levels, semantically correct tables with visually distinct headers and readable column spacing, numbered steps and bullets to make the reading flow clear. Avoid redundant sections and blockquote callouts. Display paths in Code-cell outputs and tracebacks relative to the repository root, using forward slashes where possible. Markdown cells render natively in Jupyter; executable work belongs in Code cells. Execute every Code cell in order and retain concise outputs. Do not render prose from Python or place the complete workflow in one oversized cell. Preserve D-044's offline default, read-only source files, in-memory processing, explicit opt-in requirement for any API path, and prohibition on notebook-generated dataset files.
- **Rationale:** Native cell types let readers see the branch purpose and relevant data before running code. Formal, concise prose, correct table structure, distinct headers, open column spacing and consistent repository-relative paths make notebook information easier to scan. Short ordered Code cells make each step visible and easier to execute and review.
- **Consequences and limitations:** Notebook validation checks the Markdown/Code cell structure, reader-first order, local links and stored outputs, then executes every Python Code cell using the offline default. Markdown cells are rendered by Jupyter and are not interpreted as Python. Successful cell execution remains distinct from scientific validity, current API state and human acceptance.
- **Status:** accepted

- **Supersedes / superseded by, if applicable:** Supersedes only D-044's requirement that all notebook cells be Python Code cells and prose be rendered from code. D-044's offline, input, and in-memory data safeguards remain in force; D-041 and D-042 remain in force for branch purpose, metadata, privacy and notebook ending.
