# Decision D-038 — Phase-specific derived-data folders

- **ID:** D-038
- **Date:** 8 October 2026
- **Question:** How should source data be arranged across successive interim phases, and which sources are implemented in this branch?
- **Context:** The user clarified that each source-specific transformation phase should have its own stable folder beneath the source's interim directory. The earlier D-037 convention used one top-level derived file per source. The user also explicitly limited code in this branch to OBIS and asked that Bio-ORACLE remain documentation-only.
- **Options considered:** Keep one interim file per source; create timestamped output folders for every run; or create a stable source/phase hierarchy, replacing outputs within each phase and using fixed paths between phases.
- **Evidence and source references:** The project's analytical workflow separates acquisition, source quality, cleaning, integration and later preparation. The data conventions require preservation of original payloads and reproducible transformation lineage. See [data storage and provenance](../data/data-storage-and-provenance.md) and the [ML workflow](../ml/ml-workflow-and-evidence-gates.md).
- **Decision:** Keep timestamps in raw acquisition snapshots. At the first OBIS raw-to-interim CSV handoff, accept the selected raw CSV path and write a validated, byte-for-byte copy to `data/interim/obis/source_validation/occurrences.csv`, with a timestamp-free `manifest.json` beside it. Put each later OBIS transformation in its own stable subfolder under `data/interim/obis/`; scripts read the preceding phase's fixed output and write their own fixed destination. Document the same source/phase folder pattern for future Bio-ORACLE work, but add no Bio-ORACLE code or acquisition to this branch. Cross-source integration and processed outputs use fixed, timestamp-free destinations when implemented; the planned analysis-ready destination remains `data/processed/modeling_dataset.parquet`.
- **Rationale:** A source/phase hierarchy preserves the lineage and purpose of each derived version. Selecting the raw run once makes the first OBIS handoff reusable; fixed paths between phases prevent downstream scripts from depending on typed timestamps. Replacing output within a phase avoids accumulating copies from repeated runs.
- **Consequences and limitations:** The current [`stage_obis_csv.py`](../../src/data_preparation/stage_obis_csv.py) checks CSV row widths and stages exact bytes; it does not clean, filter, deduplicate or transform fields. Scientific cleaning rules remain pending. Bio-ORACLE's folder layout is documented only, with no source-specific code or data in this branch. Integration and processed outputs are conventions, not generated datasets. Raw snapshots are retained and repeated downloads may increase local storage.
- **Status:** Accepted refinement of D-037; OBIS source-validation handoff implemented; scientific cleaning and downstream transformations pending.
