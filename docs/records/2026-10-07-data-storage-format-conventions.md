# Data and model artefact storage conventions

- **Date:** 7 October 2026
- **Status:** Accepted project guidance; resource and implementation details pending
- **Purpose:** Record the OCEAVERA source, derived-table and model-artefact format conventions, and the boundary between OCEAVERA analysis and possible BLUEVERSE integration.
- **Decision:** Preserve raw inputs unchanged in the publisher-delivered format. Use GeoParquet for compatible derived spatial tables and Parquet for compatible non-spatial modelling tables. Retain full environmental arrays in their source format and extract selected location-level values into derived tables instead of flattening complete rasters. Use JSON for compact manifests, metadata and metrics. Record actual formats and specification/serialization versions where relevant. Select model serialization only after the model and environment are agreed; Joblib for a compatible scikit-learn artefact and native JSON/UBJSON for XGBoost are conditional examples, not selected frameworks.
- **BLUEVERSE integration boundary:** The discussed handover pattern uses PostgreSQL/PostGIS for operational spatial records, JSON for ordinary API messages, GeoJSON for modest spatial API features, and separate file/object storage for large analytical assets. Confirm the receiving integration contract before implementation. COG (`.tif`) and ONNX (`.onnx`) remain optional, unfinalised future integration suggestions only; neither is an OCEAVERA requirement, deliverable or current format selection.
- **Rationale:** Preserve each publisher's source and array structure, avoid unnecessarily converting complete environmental rasters into tables, and choose derived formats that retain spatial metadata or support tabular ML use as appropriate. Keep OCEAVERA's research datasets separate from any operational BLUEVERSE data store.
- **Options considered:** Store all data as CSV/JSON; preserve all source formats and select derived formats by role; treat COG and ONNX as core OCEAVERA outputs. The accepted guidance is the second option. CSV, NetCDF, GeoParquet, Parquet, JSON, Joblib, XGBoost native formats, PostgreSQL/PostGIS, GeoJSON, COG and ONNX have the roles described in the [canonical storage guide](../data/data-storage-and-provenance.md); examples do not establish that any input resource, framework or integration is implemented.
- **Evidence and source references:** User request of 7 October 2026 to apply the supplied data-storage analysis and clarify COG/ONNX status; [GeoParquet v1.1 specification](https://geoparquet.org/releases/v1.1.0/), [Apache Parquet](https://parquet.apache.org/), [Unidata NetCDF data model](https://docs.unidata.ucar.edu/netcdf-c/current/netcdf_data_model.html), [Joblib persistence security guidance](https://joblib.readthedocs.io/en/latest/user_guide/persistence.html), [XGBoost model I/O guide](https://xgboost.readthedocs.io/en/stable/tutorials/saving_model.html), [PostGIS manual](https://postgis.net/documentation/manual/), [GDAL COG driver](https://gdal.org/en/stable/drivers/raster/cog.html) and [ONNX introduction](https://onnx.ai/onnx/intro/).
- **Consequences and limitations:** Source acquisition, exact publisher packaging, model family, dependency/runtime, artefact size/rights, dataset compatibility and BLUEVERSE interface remain unverified or undecided. The current `raw/`, `interim/` and `processed/` directories remain in use; no parallel Bronze/Silver/Gold hierarchy is introduced. The format guidance does not authorise data acquisition or model/integration implementation.
- **Related decision:** D-032 in the [decision register](../project/decision-register.md).
