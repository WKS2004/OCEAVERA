# Decision D-044 — Executable branch work notebooks

- **ID:** D-044
- **Date:** 8 October 2026
- **Question:** How should branch work notebooks execute, obtain inputs and retain results?
- **Context:** The first biological data collection branch notebook used documentary excerpts in unexecuted code cells. The user clarified that branch work notebooks must run cell by cell, accept either a saved source file or a third-party API as input, and retain the work within the notebook rather than writing a result dataset to disk.
- **Options considered:** Keep code excerpts unexecuted; put prose in non-executable Markdown cells; or make every branch-work notebook cell executable Python, render prose through notebook display, and keep analysis data in memory.
- **Evidence and source references:** Explicit user direction on 8 October 2026; the maintained [OBIS downloader](../../src/data_collection/obis_occurrences.py), [JSON-to-CSV converter](../../src/data_collection/obis_json_to_csv.py), current [branch notebook](../../notebooks/branch_work/01_pipeline_biological_data_collection.ipynb), and [OBIS API](https://api.obis.org/).
- **Decision:** Every cell in a branch work notebook must be an executable Python code cell. Render explanatory sections from code with the notebook Markdown display facility. Execute cells in order and retain concise, reviewable outputs in the notebook. Inputs may be read from an existing data file or retrieved from a public API; API access must be an explicit opt-in and remain disabled in default execution. Keep fetched source records and derived tables in memory, use in-memory streams for tabular demonstrations, and do not write notebook-generated data files to disk or embed complete raw payloads in saved outputs. Preserve the existing contributor metadata and branch section conventions under D-041 and D-042.
- **Rationale:** Executable cells make the notebook reproducible and expose errors at the place they occur. In-memory processing records the demonstrated work without creating a second dataset export or imposing unrequested network traffic.
- **Consequences and limitations:** The branch notebook must pass a full ordered execution using its documented offline default. A notebook may include an API path, but its default configuration must not send requests; an API run is a separate user action and can consume network data. Saved outputs should report useful counts, checks and limits without duplicating full payloads. Local file modes must remain read-only. This convention does not replace the verified raw JSON/CSV acquisition scripts, their manifests or provenance records, nor does it establish scientific cleaning or modelling results.
- **Status:** accepted for input, network and persistence safeguards; superseded by D-045 for the notebook cell-type and reader-sequence rule
- **Affected documents and artefacts:** [Notebook index](../../notebooks/README.md#branch-work-notebook-convention), current [branch notebook](../../notebooks/branch_work/01_pipeline_biological_data_collection.ipynb), [root README](../../README.md), [contributor guidance](../../CONTRIBUTING.md), [root agent instructions](../../AGENTS.md), [readiness review](../project/repository-readiness-and-alignment.md), [workflow guide](../project/github-workflows.md) and agent resources.
- **Supersedes / superseded by, if applicable:** Supersedes D-041's documentary-code and no-acquisition restrictions for branch work notebooks. D-041 remains in force for purpose and general structure; D-042 remains in force for the contributor table and notebook ending. D-045 replaces the all-Code-cell implementation with native Markdown narrative and executable Python Code cells while retaining D-044's offline, read-only and in-memory data safeguards.
