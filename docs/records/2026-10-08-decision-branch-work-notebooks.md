# Decision D-041 — Branch work notebooks

- **ID:** D-041
- **Date:** 8 October 2026
- **Question:** How should a completed branch's implementation and evidence be summarised for review and handover?
- **Context:** The user requested a notebook at branch finalisation that describes the work of the branch, with a repeatable structure for future branches. Existing contributor logs and scientific records already serve different purposes and must not be replaced by this notebook.
- **Options considered:** Keep branch details only in source and commit history; create branch-specific Markdown summaries; create one Jupyter notebook per finalised branch and maintain a shared structure in the notebook index.
- **Evidence and source references:** The current branch has three OBIS intake/staging scripts, associated source and decision records, repository automation and documentation. The [notebook index](../../notebooks/README.md) defines future analysis notebooks, while the [contributor recording rule](../../.agents/rules/ai-usage.md) and [scientific record conventions](../../CONTRIBUTING.md#project-evidence-records) cover other evidence types.
- **Decision:** At branch finalisation, create or update one branch work notebook at `notebooks/branch_work/<branch_name>.ipynb`. Derive the lowercase snake-case filename from the branch name by replacing separators such as `/` and `-` with `_`. Use the documented section order for metadata, scope, branch results, code components, data/provenance, environment/dependencies, checks/limits and references/handover. Create it after implementation, documentation and requested checks are complete. D-042 later refines the original metadata and ending requirements.
- **Rationale:** A consistent branch-level overview makes implementation and handover reviewable without relying on conversation history, while canonical source code, decisions, scientific evidence and contributor logs remain authoritative for their respective facts.
- **Consequences and limitations:** The original D-041 convention omitted registration numbers and other academic identifiers. D-042 supersedes that restriction only for the `Registration Number` column of the branch-notebook contributor table; registration values remain excluded from every other repository artefact, including logs and verification output. Notebooks must use verified project attribution and omit institutional identity forms and email addresses. They must not assert personal contribution, human acceptance, scientific validity or completion beyond linked evidence. Keep complete maintained implementations in source files; include concise, reviewed code excerpts and links. D-044 supersedes the documentary-code and no-data-acquisition restriction for branch notebooks: Python Code cells execute, API input is opt-in, and notebook data remains in memory without dataset files. D-045 requires native Markdown cells for narrative and concise executable Python Code cells for operations. Do not embed raw payloads or credentials. Analytical notebook execution remains governed by its own evidence and environment requirements.
- **Status:** refined by D-042, D-044 and D-045; the branch-notebook purpose and general structure remain in force
