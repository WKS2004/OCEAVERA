# Documentation naming and consistency

Apply when changing documents, directories or local references.

- Name a document after its contents using familiar terms: overview/scope, workflow, requirements/evidence, decisions, storage/provenance or readiness. Keep its title and index description consistent.
- Use the [knowledge map](../repository-map.md) to identify the authoritative document for a fact. Link to it rather than duplicating mutable status or scope in multiple guidance files.
- Rename the actual file and update all links, registry references, workflow instructions and indexes in the same change. Do not retain duplicate old versions as navigation aliases.
- Keep local references relative to their containing file and within the repository. Do not name absent local reference artefacts or machine-specific paths.
- Separate templates from dated records and planned requirements from established evidence. Preserve historical findings while updating their navigation links after a rename.
- At branch finalisation, add or refresh `notebooks/branch_work/<branch_name>.ipynb` after the other branch work is complete. Follow the [branch notebook structure](../../notebooks/README.md#branch-work-notebook-convention); use it to describe actual branch artefacts, not to assert individual contribution or acceptance. Include a contributor table headed `Registration Number`, `Member Name` and `GitHub Account`; D-042 permits registration numbers only in that table. Exclude other academic identifiers, credentials and raw payloads, and never copy a registration number to logs or other repository artefacts.
- Branch-work notebooks use native Markdown cells for narrative and executable Python Code cells for operations. Put the title, contributor table, purpose, scope and data context before the first Code cell. Keep Code cells concise and ordered; do not render prose from Python or combine the whole workflow into one large cell. Execute every Code cell in order and retain concise results. Use saved data read-only or make API retrieval an explicit opt-in; default execution must not access the network. Keep data in memory and do not write notebook-generated dataset files to disk.
- Keep UTF-8, LF, a final newline and no trailing whitespace. Use complete, clear British English and disclose pending evidence.
- Put complete commands and standalone source/configuration snippets in fenced code blocks so readers can copy them. Keep short identifiers, field names, paths, flags and placeholders inline when they are references rather than complete examples.
- Apply [member privacy](../../CONTRIBUTING.md#member-privacy) to public documentation and outputs. Extract responsibilities from academic submissions without copying member-specific identity fields or individual assessment records.
